# 周期判定与恢复合同

## 事实与职责

插件决定关联 Key 的日、周用量何时清零，并按设置在清零后发送模型测试与邮件；不创建 Key、不改金额上限、路由或宿主原生窗口
一个 Key 关联一个账号，一个账号可关联多个 Key，各 Key 独立计费与处理
只使用主动刷新得到的唯一 `codex:604800s`、604800 秒窗口及非空观测时间、重置时间
缓存只展示，使用率下降不参与判定，旧样本与缺失窗口不触发清零
新增关联只建立基线；暂停后恢复重新建立基线，不补做历史周期

## 判定

Rref 为已确认结束时间，Tprev 为上一有效观测时间，T 和 R 为新观测及结束时间
W 为 7 天，S=R−W 为新窗口起点，容差 τ 为 2 分钟

| 条件 | 行为 |
| --- | --- |
| T≤Tprev | 保留基线，退避重查 |
| abs(R−Rref)≤τ | 同周期，只更新观测时间，不移动已确认结束时间 |
| R>Rref+τ 且 min(Tprev,Rref)−τ≤S≤T+τ | 确认新周期 |
| 新周期且 S≥Rref−τ | 正常换周，自动清零 |
| 新周期且 S<Rref−τ | 提前重置，默认自动；关闭开关后等待确认 |
| 其他边界变化 | 等待人工确认，不自动清零 |
| 目标窗口缺失、空结束时间、刷新失败 | 保留基线，有界退避 |

到点后上游仍返回旧窗口不视为换周，漏过多个周期只处理当前周期
账号通常每 5 分钟检查一次，maintenance 每轮处理有限账号和待重置 Key
多个 Key 共用账号刷新，持续无法刷新超过 1 小时显示需处理

首次确认正常换周或提前重置后，仍立即按设置自动清零一次。完成的关联进入持久的“等待周期固定”阶段；只要结束时间仍随观测时间后移，就不为同一次变化再次清零，也不追加“提前重置”事件。新建关联、暂停后恢复遇到此类窗口时只等待固定，不补清零。
等待阶段仅由有效主动刷新推进：新结束时间不再接近观测时间加 7 天，连续两次有效观测至少间隔 5 分钟，结束时间保持固定（毫秒时间戳变化不超过 1 秒），才将当次窗口确认为基线；候选继续移动则重新计时。完成后恢复正常周期识别，不补做清零。下一完整周周期已越过上次结束时间时，仍可独立按正常换周处理。
旧状态缺少等待阶段字段时保守进入等待，不重放旧清零；无法确认的迁移期间周期可能被跳过。上游未提供周期身份，同一段未固定期内的真实再次重置若与时间漂移无法区分，合并为同一周期，不重复清零。

## 清零与恢复

读取预算快照 → 用精确状态版本保存重置意图 → 调用一次 `all` 清零 → 保存完成
`all` 在宿主同一事务中同时清零日、周用量，不拆成两次调用；拆分会出现只清一项后结果未知、无法安全补做另一项的状态
私有状态写入与预算清零不是同一事务，不能假定跨操作原子性
任何未完成意图都视为结果未知，包括意图落盘后进程退出、清零响应丢失、完成落盘失败
结果未知停止自动重试，读回预算只作辅助展示，不能据此证明成功

默认人工动作保留现有用量并重新建立基线，再清零一次必须明确确认可能删除期间新消费
正常失败在调用清零前发生时仍可重试；多个 Key 独立处理，已完成和结果未知的 Key 不会自动重复
排队样本超过 5 分钟时取消该次排队并重新检查当前周期，停机恢复不直接补做旧样本的清零
管理操作与维护串行，状态版本比较防止过期页面或并发进程重复领取
每个关联保留最近 10 条事件，记录时间、原因和必要错误分类，不记录原始上游错误正文
首次清零成功时每个 Key 记录一次原因与处理时间；内部等待、候选更新、周期固定及页面刷新不追加或改写该事件。真实失败与未知结果继续按原规则记录。

## 重置后的测试与邮件

只有清零返回成功且完成状态已持久化，才创建独立发送任务；首次基线、恢复、跳过与未知清零均不发送
任务按关联记录递增 ID、重置时间、当时收件地址与测试/邮件状态，多个周期不会覆盖旧任务
每次维护最多执行一个发送动作，测试先于邮件；模型测试最多等待 20 秒，SMTP 最多等待 8 秒，维护总期限 25 秒
发送前将对应状态保存为 `unknown`，完成后保存 `succeeded`；超时、断连、外部错误或完成保存失败保留未知，不自动重发
未知测试不阻挡邮件，邮件说明实际状态；管理员确认重复消费或重复投递风险后，可独立重试测试或邮件，重试不调用清零
暂停关联和关闭对应开关均停止发送，重新启用后继续排队任务；关闭测试但继续发送邮件时，该次待测试记为跳过；邮件使用重置时的收件地址，重试使用当前 SMTP 配置
每个关联保留最近完成记录与全部未完成记录，上限 32 条，全插件发送记录上限 128 条；积压满时清零继续，新通知跳过并记录事件
SMTP 配置和密码保存在插件私有状态；管理 GET 响应移除密码内容，空密码更新保留旧值，显式清除单独控制；传输只支持校验证书的 TLS/STARTTLS

## 手动发送测试

关联详情通过单独确认立即调用模型或 SMTP，不清零、不刷新账号、不更新周期基线，也不创建或修改自动发送任务
每个关联独立保存最近一次 `last_manual_probe` 和 `last_manual_mail`，含时间、状态及邮件的当时收件地址；旧状态缺失字段默认为空
手动动作检查精确版本、显式确认与关联；邮件无视自动开关但要求已保存的完整 SMTP 和非空有效邮箱，主题与正文明确为 SMTP测试
先 CAS 保存 `unknown` 意图再调用一次外部服务，成功后保存 `succeeded`；错误、超时、断连或完成落盘失败保持未知，维护和刷新不领取这些记录
两类动作共用管理串行锁，模型最多等待 20 秒、邮件 8 秒；暂停关联及自动开关关闭不阻止显式手动测试
页面使用独立确认状态、防重复点击，动作后读回持久结果；响应或刷新失败提示先刷新核实，重复测试需重新确认

## 日限重置卡（拼车一期）

本节为 2026-10-28 与用户确认的一期合同，自 0.3.0-beta.1 起生效。插件显示名改为"拼车一体化管理插件"，插件 ID `haohex.key-reset-follow` 与仓库名不变

### 发卡

- 每个关联有独立的"日限重置卡"开关，默认关闭；暂停的关联不发卡，恢复后不补发
- 每个关联维护周期序号 `cycle_seq`，只在插件确认账号进入新周期时加一：自动或人工清零成功、清零结果未知、管理员对 Confirm（提前或无法解释的周期变化）选择"忽略并更新基线"。窗口标识变化（Changed）不能证明进入新周期，不加一；对结果未知的再清零或跳过、等待周期固定阶段的候选变化、页面刷新都不加一
- `cycle_seq` 加一时，若开关开启，作废旧卡并发放 1 张属于新序号的卡；卡不累积，下一周期作废
- 开关从关到开时，若当前序号尚未发过卡，立即发 1 张；同一序号内反复开关不重复发卡。新建关联时开关为关闭，开启即按此规则发卡

### 用卡

- 成员在拼车页用自己的 Key 用卡，只清零该 Key 的当日用量：调用一次 `reset_key_budget(period=daily)`
- 用卡前读取预算并拒绝：未设日限额（`daily_limit_usd` 为 0）、今日用量为 0、周限额非 0 且本周用量已达周限额、卡不属于当前 `cycle_seq`、关联暂停或开关关闭
- 用精确状态版本先把卡保存为"使用中"，再调用一次清零，成功后保存"已使用"；调用前失败恢复为可用。清零返回错误、超时、断连或完成落盘失败均记为"结果未知"，视为已用，不自动重试，由管理员核实
- 用卡与维护、管理动作共用串行锁；等待锁超过 5 秒返回"稍后再试"，不排队
- 用卡成功或结果未知后，SMTP 已启用且关联有收件邮箱时排队一封通知邮件，沿用"先保存 unknown 再发送一次、未知不重发"的规则
- 未完成的卡通知每个关联最多 8 条、全插件最多 64 条；达到上限时用卡照常完成，本次不排队邮件并记事件。管理员可用 `card_notice_clear {key_id, version, acknowledge}` 确认后删除该关联全部结果未知的卡通知，不重发

### 拼车页与统计

- 成员页固定路径 `/carpool`，由 `http` 中间件提供页面与 `/carpool/api/*` 接口；每次接口请求携带 `Authorization: Bearer <Key>`，插件用 `host.client.verify` 换取 Key ID，不保存、不记录 Key 原文。页面只把 Key 保存在内存
- 验证失败按来源 IP 限制为每 60 秒 10 次、全局每 60 秒 200 次，超限返回 429；所有响应 `Cache-Control: no-store`
- 页面展示：自己的 Key 全名与卡状态；同账号拼车成员按本周期花费占比降序排列，自己标"我"，其他 Key 名称保留首尾各 1 字、中间用 `*`；不展示其他成员金额
- 占比 = 该 Key 本周期花费 ÷ 账号本周期花费。本周期为 [账号周窗口结束 − 604800 秒, 现在)。分子取管理统计 `/api/admin/usage/insights/diagnostics?dimension=apiKey`，分母取同接口 `dimension=account`，均使用同一 `startTime`/`endTime` 和 `estimatedCost`，经 SDK `dispatch_http` 以插件身份调用
- 账号花费减去各拼车 Key 花费的差值（小于 0 计 0）显示为"其他"；Key 同时使用其他账号时分子会包含其他账号花费，属已知偏差
- 统计由维护任务每 10 分钟刷新一次并只存内存；成员接口只读缓存，不在请求路径上调用统计接口；缓存为空时显示"统计生成中"

### 管理与成员接口

- 管理动作：`card_toggle {key_id, version, card_enabled}` 按"发卡"规则开关并在需要时发卡；`card_refund {key_id, version, acknowledge}` 仅对当前序号、状态为结果未知的卡，管理员勾选"已核实未清零"后恢复为可用并记事件。管理 GET 额外返回 `shares`（账号 ID → `ShareStats`，管理员可见金额）
- 关联详情显示卡状态、开关与拼车页地址 `/carpool/`；占比缓存的周期结束时间与账号当前周窗口相差超过 2 分钟或缺少该 Key 时，管理页与成员页都显示"统计生成中"，不把旧周期数据当作本周期
- 成员页资源随包发布在 `web/carpool/`（`index.html`、`carpool.js`、`carpool.css`），插件启动时按可执行文件位置读入内存；读取失败只让成员页返回 503。`/carpool` 重定向到 `/carpool/`，页面用相对路径加载脚本与样式
- `GET /carpool/api/me` 返回 `key_name`、`paused`、`card_enabled`、`card`（仅当前序号的卡：`status`、`issued_at`、`used_at`，否则 null）、`cycle`（`start_ms`、`end_ms`）、`budget`（仅本人日、周用量与限额）、`can_use_card`、`card_block_reason`、`shares`（`computed_at`、`items[{label, me, percent}]`、`other_percent`，缓存为空时 null）
- `POST /carpool/api/card/use` 返回 `{result: "used" | "unknown", message}`；错误统一 `{error}`：401 Key 无效、404 未加入拼车、409 不满足用卡条件、429 尝试过多、503 繁忙或资源不可用
- 成员接口不返回账号邮箱、其他成员金额、Key ID 或完整名称

### 不阻塞 API 的硬性要求

- 中间件处理函数第一步判断路径，只接管去掉查询串后等于 `/carpool` 或以 `/carpool/` 开头的请求（`/carpoolx` 等同名前缀放行），其他请求立即交还宿主；在此之前不读状态、不调宿主接口、不等待任何锁
- 成员页处理捕获 panic 并设置超时，失败只返回成员页错误；非成员路径不因成员页、维护或发信异常而失败
- 宿主为新注册的 `http` 挂载默认使用"拒绝"失败策略（CPR 3.34、3.35 `artifacts.rs`），插件清单无法改变。插件进程不可用时该策略会拒绝全部请求，因此每次安装或升级到含中间件的版本后，管理员必须立即在高级设置把 HTTP 挂载的失败处理改为"委托"，并调用一次 API 确认正常；README 与发布说明必须写明此步骤
- 宿主只在插件不可用且策略为"委托"时放行；插件已接手的请求若超时或进程中途退出，该请求会失败且不重放，这是无法由插件消除的残余风险。紧急处理：在高级设置关闭 HTTP 挂载，其余功能照常运行
- 每个版本发布前在隔离宿主做慢插件与崩溃注入测试，确认非成员路径的 API 请求不受影响，结果写入 PR

## 账号点数与重置卡（拼车二期）

本节为 2026-10-29 确认的二期合同，自 0.3.0-beta.2 起生效。二期只读展示，不改变一期的发卡、用卡、清零与"不阻塞 API"规则；宿主范围改为 CPR 3.35（`>=3.35.0, <3.36.0`），SDK 固定到 v3.35.0 提交

### 数据来源

- 点数：SDK `quota_details`（`host.data.quota.details`）的 `credits`（`has_credits`、`unlimited`、`balance`）。该调用只读宿主已有观测，不触发上游刷新；宿主无点数事实时为 null
- 上游重置卡：管理接口 `GET /api/admin/accounts/reset-credits?accountId=<账号 ID>`，经 `dispatch_http` 以插件身份调用。外层为 `{code, message, data}`，`data` 为 `{availableCount, credits[{id, status, title, expiresAt, expiresAtDisplay, resetType}]}`。该接口每次实时查询上游，并可能触发凭据刷新
- 插件不调用消费重置卡（同路径 POST）或自动使用开关等写接口，不保存、不返回上游卡 `id`；到期时间取 RFC3339 的 `expiresAt` 转为毫秒，不使用宿主时区的 `expiresAtDisplay`

### 刷新与缓存

- 两类数据都只存内存，进程重启后为空；成员接口与管理 GET 只读缓存，请求路径上不调用 `quota_details` 或重置卡接口
- 维护任务在清零、发信和占比统计之后刷新，期限取维护剩余时间；单次重置卡请求超时 5 秒，每次维护最多查询 1 个账号的重置卡，不挤占清零与发送
- 点数：每个有拼车关联的账号最多每 10 分钟读取一次
- 重置卡：按需刷新，只查询最近 30 分钟内在管理页或成员页被查看过、且距上次尝试已满 10 分钟的账号；无人查看时不访问上游。失败只记录 `reset_cards_failed_at` 并保留旧数据，成功后清空失败时间
- 关联删除后同步删除对应账号的缓存与查看记录

### 展示

- 管理 GET 额外返回 `account_info`（账号 ID → `AccountInfo`）；关联详情的"概览"显示该关联账号的点数与重置卡
- `GET /carpool/api/me` 额外返回 `account`（本人关联账号的 `credits`、`credits_at`、`reset_cards`、`reset_cards_at`、`reset_cards_failed_at`，无缓存时为 null），不返回账号 ID、邮箱或名称
- 点数：`unlimited` 显示"无限"，`has_credits` 为 false 显示"无点数"，否则原样显示 `balance` 文本；为 null 时显示"暂无数据"
- 重置卡：显示可用数量与各卡的标题（缺失时显示"额度重置卡"）、类型、状态和北京时间到期时间，按到期时间升序；从未获取成功显示"获取中"，有失败时间时提示"最近一次获取失败，显示的是 X 的结果"
- 两类数据都显示获取时间；页面不提供刷新或消费按钮

## 页面与设置

主列表分列显示 Key 与关联账号、本周用量、账号使用百分比、账号预计重置和状态；名称与邮箱不重复展示。金额显示两位小数，完整精度和 Key 自身的周用量重置时间在详情查看。

提前重置开关与发送设置集中在插件设置页面，编辑后显式保存，取消不写入状态。保存使用状态版本检查，不重置基线、不触发清零，也不清除待确认或未知结果。

页面所有日期、事件与邮件时间固定按北京时间 UTC+8 显示，不提供时区选择；判定继续使用原始时间戳。旧状态中的 `display_timezone` 字段仅为兼容保留并原样保存，不再影响显示，不要求重新建立关联。

## 已知限制

清零同时关闭宿主日、周窗口，下次使用时分别按宿主时区重新开启；日用量在账号换周时额外清零一次，不改变 Key 自身的每日自然重置
Key 可能比账号窗口提前约 24 小时自然清零一次，插件不改变原生到期时间
上游可能直到首次使用后才给出新周期；插件先等待有效样本并确认清零，只有启用测试时才在清零后发送模型请求
提前重置与边界校正在事实层面不能完全区分，所以保留自动开关和人工处理
停用或卸载停止未来动作，不能撤销已完成清零

判定边界由 `tests/cycles.rs` 固定，持久化失败、部分失败和并发恢复由 `tests/recovery.rs` 固定
这些逻辑测试不能替代真实宿主联调
